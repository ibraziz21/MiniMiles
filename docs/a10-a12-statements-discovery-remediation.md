# A10–A12: statements, exports and discovery availability

29 October 2026. Implemented in the working trees; Platform migration 165 is applied only to synthetic branch `urjamfbtlzycetvuvwpg`. Production remains unchanged. This is remediation evidence, not release approval.

**Subsequent test triage:** the 11 merchant failures and Hub email assertion described below are now resolved. Full unit suites pass (331 merchant; 1,127 Hub with one skip), and both typechecks pass. No runtime application changes were needed. See [triage evidence](release-test-triage-2026-10-29.md). The test failures are no longer release blockers; the remaining acceptance and deployment tasks still apply.

## Changes

**A10 — safe, complete exports.** The authenticated statement endpoint now has an independent `?export=csv` path. It reads 200 rows at a time and streams the complete history, regardless of the visible UI page. Receipt/payment references are quoted, embedded quotes are escaped, controls are replaced with spaces, and leading-whitespace formula prefixes (`=`, `+`, `-`, `@`) are prefixed with an apostrophe. This is a spreadsheet-literal CSV policy: other CSV consumers may display that apostrophe. Trusted monetary values use canonical decimal cells, so a negative reversal remains numeric. Invalid money or statement metadata is unavailable, never an invented amount. A failed stream makes the browser's blob read fail; the UI only downloads after that read completes and otherwise shows an export error.

**A11 — unavailable is distinct from empty.** Funded allocation, secondary-membership, membership-set and participant-profile failures now raise a typed availability error. Unknown/missing/inactive/hidden participants still withhold the offer. The catalogue, both Home variants and merchant pages show a retry notice; relevant v1 endpoints return retryable 503 rather than a successful empty catalogue. The public catalogue error explicitly forbids caching. A structured `funded_discovery_unavailable` log records the stage and affected allocation IDs without credentials. A participant resolution failure conservatively withholds that discovery batch, including otherwise resolvable offers; it does not advertise a partial set. A successful empty query and an intentionally disabled feature remain ordinary empty results. Alert delivery is not configured by this change.

**A12 — bounded statements.** Home calls an aggregate-only RPC. Statement history uses 50-row pages ordered by `(redeemed_at DESC, voucher_redemption_id DESC)` with an opaque, validated keyset cursor. SQL enforces 1–200 rows per call. Totals always cover the complete merchant ledger and preserve actual paid cash after reversal; they are never calculated from the visible page. Export uses the same ordering with 200-row pages. Merchant scope always comes from the session, including exports; request merchant identifiers have no effect. Both new RPCs are service-role-only. Responses prohibit caching.

Export traverses current records across successive database snapshots, rather than representing a transactionally frozen financial statement. Newer redemptions do not shift its keyset pages; payment/reversal state may change during a long export. A legally fixed or audited statement would need a materialized export snapshot/job. The current CSV is an operational history export.

## Rollout and remaining release blockers

Migration 165 deliberately retires the old unbounded statement RPC by raising `STATEMENT_CLIENT_UPGRADE_REQUIRED`. Deploy the new merchant app and migration as a coordinated change: an old app encountering 165 returns unavailable instead of silently calculating a partial balance. Do not roll the app back without considering this database contract. Apply earlier financial/lifecycle migrations 160–164 in their verified dependency order first. Main migration history/order still needs environment-specific reconciliation.

The full Hub unit run currently has 1,123 passes, one skip and the known account-deletion support-email assertion failure (additional focused discovery cases were then added and passed). The full merchant run has 313 passes and 11 failures in directory contact, directory presence and discovery-media tests; the repaired voucher pricing/reimbursement files pass. Those failures involve version-token fixtures, missing query mocks and media/rate-limit contracts. They are observed failures in untouched areas, not proven pre-existing failures or permission to waive them.

The branch merchant UI still reports an unavailable Merchant Terms status because migration 153's RPC is absent there. Its separate review/reconciliation remains required. Production database/app/worker rollout, the remaining admin/operator matrix, real camera/assistive-technology checks and external payment/delivery integrations are not certified by these journeys. Release remains blocked pending the relevant gates and failing-suite reconciliation.
